# Findra Plan 4 - Content

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Findra searches what is *inside* files, with no model and no download. An FTS5 store, a document text extractor, an indexer child process, a queue fed from the USN journal the helper streams, and the two diagnostics that make the whole thing checkable and publishable - `--searchindex` and `--searchbench`.

**Architecture:** The elevated helper gains a journal tail and a `Subscribe` push channel; it forwards raw records and decides nothing. The UI owns the policy - what is eligible, what gets queued, where the consumed USN sits - and writes it into a SQLite database under `%LOCALAPPDATA%\Findra\index\`. A child process, `findra.exe --index <parentPid>`, drains that queue, extracts text, and writes segments and FTS rows back. The database is the whole handoff between UI and indexer: no second pipe, no protocol, and it survives either process dying mid-write.

**Tech Stack:** .NET 10 (`net10.0-windows`), Microsoft.Data.Sqlite 10.0.11 (FTS5), PdfPig 0.1.16, SkiaSharp 3.119.4, Avalonia 12.1.1, xUnit.

**Spec:** `docs/superpowers/specs/2026-09-01-findra-design.md` - §2a install/resume/uninstall, §3 processes, §4 data locations, §5 subsystems, §6 capabilities, §9 verification, §9a the README, §10 testing, §12 decisions.

**Reconnaissance:** `.superpowers/sdd/plan-4-recon.md` - the per-file inventory of the port source, the schema verbatim, and the all-or-nothing gates with file:line. Treat it as accurate.

## Global Constraints

- **Target framework stays `net10.0-windows`.** Nothing in this plan may bump it. The WinRT-dependent files (OCR, media decode, shell thumbnails) need `net10.0-windows10.0.19041.0` and they are Plan 5's; the moment one of them is ported the TFM moves and every project in the tree moves with it. Publish stays self-contained via the publish command, never a csproj RID.
- **Exactly two packages are added: `Microsoft.Data.Sqlite` 10.0.11 and `PdfPig` 0.1.16.** Not ONNX Runtime, not Whisper.net, not NAudio, not System.Numerics.Tensors. If a file you are porting needs one of those, you are porting a file that belongs to Plan 5 - stop and say so.
- **This plan is model-free.** Words in documents is free and always on (spec §6: *"free" is printed on the documents row*). No `ModelStore`, no `Encoders`, no `VectorStore`, no embedding, no download. A kind the indexer has no decoder for is marked **Skipped** with a reason, never Failed and never blocking.
- **The elevated helper decodes nothing.** It forwards journal records and reconstructs paths. Every eligibility rule - `FileKinds.HasContent`, exclusions, repo roots, size caps - is evaluated in the UI at normal integrity. Spec §3: *the elevated helper opens a volume handle and scans bytes; it never parses untrusted file content.*
- **"Done" is a fact the index records, not a guess** (spec §2a): schema version, consumed USN position per volume, pending queue. A non-empty queue is **resumed**, never cleared. An index that was finished is never re-walked.
- **Name search stays async everywhere.** No `.Result`, no `.Wait()` anywhere in library or UI code. `GetAwaiter().GetResult()` may appear **only** at a `Program.Main` switch arm, where there is no async context to await into. `Indexer.Run` is synchronous, so `--index` needs none; this plan adds exactly one, at `--searchbench`, and no other `GetAwaiter().GetResult()` is permitted anywhere.
- **Every published or displayed number is formatted with `CultureInfo.InvariantCulture`.** The project sets `<InvariantGlobalization>false</InvariantGlobalization>`, so a bare `{n:N0}` renders `3.000` on a German machine and `48,0 GB` on a Hebrew one. The `--searchbench` fragment is pasted into the README verbatim (§9a) and the status line is compared in tests; both must read the same on every machine.
- **Every query still carries a generation counter.** The journal push channel is deliberately outside it: a pushed event is not an answer to anything, so it carries no generation and must never touch `Generation`.
- **No lineage anywhere.** Nothing in code, comments, commit messages or this document may describe Findra as derived from, forked from, or a component of another project. Referring to a source *path* while porting is fine. The name-grep (`grep -ric prism src/`) is necessary and **not sufficient**: read every ported comment and ask whether it reads as written for Findra by someone who has never seen another codebase. The comments in `ContentQueue.cs`, `Indexer.cs` and `SearchIndexProbe.cs` all name the other product and describe a widget host Findra does not have.
- **Build output pristine** - zero warnings from `dotnet build` and `dotnet test`.
- **TDD for all new code.** The ported engine arrives working and is not rewritten test-first; it gets characterization tests only where Findra changes its behaviour - here, `ContentDb` and the all-or-nothing gate becoming per-capability (spec §10).
- Commit messages carry no AI/Claude attribution.

```csharp
public const int SchemaVersion = 1;

/// <summary>One schema step. <c>InvalidatedKinds</c> is what that step made stale - and
/// nothing else is re-queued. Re-indexing a finished disk because an upgrade did not look
/// first is the worst thing this product can do to someone (spec §2a).</summary>
public readonly record struct Migration(int To, int[] InvalidatedKinds, string Reason);

/// <summary>Empty at version 1: there is nothing before it to migrate from. Plan 5 appends
/// the step that invalidates what its models change.</summary>
public static readonly IReadOnlyList<Migration> Migrations = [];
```

In the constructor, after `CreateSchema()` and only when not read-only:

```csharp
private void OpenSchema(IReadOnlyList<Migration> steps)
{
    string? stamped = Get("schema");
    int from;
    if (int.TryParse(stamped, out int v)) from = v;
    else from = HasAnyItem() ? 0 : SchemaVersion;   // never stamped + never written = brand new

    if (from == SchemaVersion) { Set("schema", SchemaVersion.ToString()); return; }
    if (from > SchemaVersion)
    {
        // A newer Findra wrote this index. Read it as-is rather than "migrating" backwards.
        Log.Warn("index", $"index schema {from} is newer than this build's {SchemaVersion} - using it as-is");
        return;
    }

    foreach (Migration m in steps)
    {
        if (m.To <= from || m.To > SchemaVersion) continue;
        int n = RequeueKinds(m.InvalidatedKinds, m.Reason);
        Log.Info("index", $"schema {from} -> {m.To}: {m.Reason}, {n:N0} file(s) re-queued");
    }
    Set("schema", SchemaVersion.ToString());
}
```

`HasAnyItem()` is `SELECT 1 FROM items LIMIT 1`.

The USN position, keyed per volume so two drives cannot overwrite each other:

```csharp
/// <summary>Where journal consumption for this volume got to, and which journal that was.
/// A different journal id means the volume's journal was recreated and the position means
/// nothing - the caller does a full pass instead of replaying from a number in another
/// journal's coordinate space.</summary>
public (ulong JournalId, long Usn)? UsnPosition(char volume)
{
    string? v = Get("usn:" + char.ToUpperInvariant(volume));
    if (v is null) return null;
    string[] parts = v.Split(' ');
    if (parts.Length != 2) return null;
    return ulong.TryParse(parts[0], out ulong jid) && long.TryParse(parts[1], out long usn)
        ? (jid, usn) : null;
}

public void SetUsnPosition(char volume, ulong journalId, long usn, SqliteTransaction? tx = null)
    => Set("usn:" + char.ToUpperInvariant(volume), $"{journalId} {usn}", tx);
```

`Set` gains the same optional `SqliteTransaction? tx = null` the other writers have, so the feeder can record the position in the **same transaction** as the enqueues it came from. Recording it outside means a crash between the two either re-queues work or loses it.

`KnownVolumes()` is `SELECT key FROM meta WHERE key LIKE 'usn:_'` mapped to its last character, sorted.

`CompileOptions()` opens a throwaway in-memory connection (`DataSource=:memory:`) and runs `PRAGMA compile_options`, returning the rows.

```csharp
public List<(string Path, string Error)> RecentFailures(int limit);              // state=2, newest indexed_at first
```

`CountsByKind` seeds the dictionary with every `ResultKind` at zero before the query. A kind that vanishes from the report because it has no rows is how "why is nothing indexed" becomes unanswerable.

- [ ] **Step 5a: Fix `RequeueKinds` - the one behavioural change to the ported store**

The source's clause is `WHERE state=1 AND kind IN (...)`: it re-queues **indexed** items only. In this plan every photo, video and audio file ends at `StateSkipped` (3), because there is no decoder for it yet. So the ported query would find **nothing** to re-queue, and the plan's whole story - a kind is Skipped now, Plan 5 picks up exactly those - would quietly never happen. Change it:

```sql
SELECT vol, frn, path, kind FROM items WHERE state IN (1, 3) AND kind IN (...)
```

`StateFailed` (2) stays out on purpose. A file the decoder genuinely could not read has not changed because a capability arrived, and retrying it on every install is a loop with no exit. Skipped means "not attempted yet"; Failed means "attempted, and it did not work".

Write that reasoning in a comment above the query. This is the modification most likely to be reverted by someone diffing against the source and concluding the plan drifted.

- [ ] **Step 5b: `OpenOrRebuild` - spec §2a's unreadable index**

```csharp
/// <summary>
/// Open the index, or rebuild it if it cannot be opened. A database whose file is truncated,
/// half-written by a lost power cycle, or replaced by something that is not a database throws
/// out of the constructor - and the only caller is a background loop, so the exception would
/// reach nobody and content search would be dead for that install with no message anywhere.
/// The unreadable file is MOVED ASIDE rather than deleted: it is evidence, it costs a few
/// megabytes, and its owner may want it. Spec §2a: rebuilt, and the UI says so.
/// </summary>
public static ContentDb OpenOrRebuild(string? path = null)
```

Try the ordinary constructor; on `SqliteException` or `IOException`, `File.Move(path, path + ".corrupt", overwrite: true)` (moving the `-wal` and `-shm` files with it), construct again, set `WasRebuilt`, and log under `index` at ERROR. `WasRebuilt` is what `IndexStatus` reads to tell the user, and it is why the flag exists rather than a bare log line - the spec asks for the UI to say so, not for the log to.

`overwrite: true` on a single fixed name means at most one `.corrupt` copy is ever kept and each rebuild replaces it, so this cannot fill a disk. (Plan 6's uninstall should know the file exists.)

**The recovery path needs its own recovery.** `File.Move` throws if the corrupt file is locked - an indexer child still holding it, an antivirus scanner mid-read - and an unhandled `IOException` there fails `OpenOrRebuild` at exactly the point it promised not to. Walk three rungs and take the first that works: the fixed `.corrupt` name; then `.corrupt-{yyyyMMddHHmmss}`, which sidesteps a lock on the first; then give up on moving anything and open `DataSource=:memory:` with `WasRebuilt` set, so content search is degraded-but-alive for this session and the next launch tries again. Never let this method throw - every caller is a background loop or a diagnostic, and neither has anywhere to put the exception.

Every caller in this plan - the UI's loop, `--searchindex`, `--searchprobe`, the self-test - uses `OpenOrRebuild`. The raw constructor stays for tests, which want a throw.

- [ ] **Step 5c: The suffix stamp, and the walk-owed latch**

`SetSuffixVersion(suffixes)` writes a stable hash of the **set** into `meta.suffixes`: lower-case each entry, sort ordinally, join with `\n`, SHA-256, hex. `SuffixesChanged(suffixes)` compares without writing. Order-insensitivity is not decoration - `ContentSuffixes()` is built from `HashSet` enumeration, whose order is not contractual, and a stamp that changed with it would re-walk every disk on every launch.

Task 4 uses this to force a fresh `FillFrom` when a later version adds an extension to `FileKinds`. Without it, an install only ever sees files matching the suffix list it was first walked with, and a newly-supported extension is invisible on every existing machine forever.

`SetWalkOwed(char)`, `WalkOwed(char)` and `ClearWalkOwed(char, tx)` are the second half, and they are here rather than in a field on `QueueFeeder` for one reason: **a debt that lives in memory is discharged by a restart, and a restart is exactly when it matters.** The key is `walk:<letter>`, per volume, because a hole on D is no reason to re-walk C.

The debt is owed whenever this process learns that events it should have seen went missing - a reset marker from the helper, a drop in the helper's outbound queue, or a rise in `NameClient.JournalDropped` on this side. It is cleared in one place only: inside `FillFrom`'s transaction, when a full pass has actually completed for that volume. Anything less than a completed walk leaves it owed.

This matters more than it looks. A dropped event is not a missed notification, it is a **hole in a range the stored cursor is about to claim as consumed**, and the claim is silent - `--searchindex` will report the index complete over files it never saw. That is strictly worse than the gap the replay path closes, because a gap at least announces itself as `NeedsFullPass`.

```csharp
private (List<ContentDb.Segment>, string?) Document(string path, long bytes)
{
    if (bytes > MaxDocBytes) return ([], "too large");
    string text = DocText.Extract(path);
    if (text.Length < 40) return ([], "no text");
    var segs = new List<ContentDb.Segment>();
    foreach (string chunk in DocText.Chunk(text))
        segs.Add(new ContentDb.Segment(ContentDb.SegText, -1, -1, -1, chunk));
    return (segs, null);
}
```

  `Vec` is `-1` - "no vector row". Plan 5 fills it in; nothing in this plan reads it.

```csharp
(List<ContentDb.Segment> segments, string? skip) = item.Kind switch
{
    ResultKind.Document => Document(item.Path, fi.Length),
    ResultKind.Photo or ResultKind.Video or ResultKind.Audio => ([], NoDecoder),
    _ => ([], "not a content kind"),
};
```

- **Status keys are namespaced.** `state` becomes `indexer:state`, and so on for `current`, `rate`, `done`, `failed`, `pending`, `beat`, `pid`. ## Task 3: The helper streams the journal, and the UI subscribes

The spec says the helper streams USN change events (§3) and the tree does not do it yet: `NtfsVolume.Read` exists, `JournalEvent` exists, and nothing connects them - `NameClient`'s pump has a `case Envelope.KindJournal: break;` waiting for exactly this task. This is the plan's centre.

It also forces a change `NameServer`'s own header predicted: *"When journal streaming lands and the index starts mutating, these readers must be serialised against the writer - one lock around replay and search."* Concurrent `Serve` calls read one shared `NameIndex` per volume, and that was safe only because the index was immutable after startup. It stops being immutable here.

**Files:**
- Create: `src/Findra/Pipe/JournalBroadcast.cs`, `src/Findra/Names/JournalTail.cs`
- Modify: `src/Findra/Pipe/Messages.cs`, `src/Findra/Pipe/NameServer.cs`, `src/Findra/Pipe/NameClient.cs`
- Test: `tests/Findra.Tests/Pipe/JournalTests.cs`
**Interfaces:**
- Consumes: `Findra.Pipe.Frame`, `Envelope`, `JournalEvent`, `Findra.NameIndex`, `Findra.NtfsVolume`.
- Produces:
  - `JournalEvent` **gains two fields**: `JournalEvent(char Volume, ulong JournalId, ulong Frn, ulong Parent, uint Attributes, string Name, string Path, uint Reason, long Usn)`.
    - `Path`, because the helper resolves it from its own index exactly as it already does for `NameRow.Path`. It has to: the UI holds no parent map and cannot turn a parent FRN into a path, and duplicating one at normal integrity is the thing the thin-helper split exists to avoid. Resolving a path from an index the helper already owns is not parsing untrusted content. A delete carries `Path = ""` - the record is gone, and the feeder keys deletes on `(volume, frn)`, which is why it never needs one.
    - `JournalId`, because a USN means nothing without it. **The feeder has to write the id alongside the position it records** (Task 4), or what it stores can never match the volume's real journal on the next launch, `ResumeFrom` answers `NeedsFullPass` every single time, and Findra re-walks every disk at every start - which is precisely the failure spec §2a says gets a test. **Every event carries it - slice events, replayed gap events, and the reset marker alike.** The three places it can silently default to zero are the three places the whole resume story dies.
  - `record VolumeCursor(char Volume, ulong JournalId, long Usn)`
  - `record SubscribeRequest(IReadOnlyList<VolumeCursor> From)`
  - `record VolumeResume(char Volume, ulong JournalId, long Usn, bool NeedsFullPass, int Replayed, string Note)`
  - `record SubscribeReply(IReadOnlyList<VolumeResume> Volumes)`
  - `Envelope.KindSubscribe = "subscribe"`, `Envelope.KindSubscribeReply = "subscribe-reply"`
  - `VolumeStatus` **gains three fields**: `VolumeStatus(char Letter, int Count, long BufferBytes, bool Live, double EnumerateMs, long NextUsn, long Dropped)` - the cold-start enumeration time and name count spec §9 requires of `--searchbench`, and the per-session dropped-event count from the back-pressure policy in Step 7.
  - **`record VolumeView(NameIndex Index, ulong JournalId, long NextUsn, double EnumerateMs)`**, declared beside `IndexLock` in `Names/JournalTail.cs`. This exists because `Serve` currently receives bare `NameIndex` objects, and a `NameIndex` knows its `Letter`, `Count` and `BufferBytes` and **nothing about a journal**. `ResumeFrom` needs each volume's current journal id and current `NextUsn`; `AnswerStatus` needs `EnumerateMs` and `NextUsn` for `--searchbench`'s `## Volumes` table. Neither has any route into the session today, so without this type both the subscribe path and half of `--searchbench` are unimplementable. `RunAsync` builds one per volume as it enumerates - it already has the `NtfsVolume`, and it already measures the enumeration (`NameServer.cs:208` logs it and throws it away).
  - `Findra.Pipe.JournalBroadcast` - `void Publish(JournalEvent e)`; `IDisposable SubscribeWithBacklog(Func<IReadOnlyList<JournalEvent>> backlog, Action<JournalEvent> sink)`; `int SubscriberCount`.
    - **The sink is `Action<JournalEvent>`, and `Publish` is `void`.** An earlier draft declared the sink `Func<JournalEvent, ValueTask>` while leaving `Publish` returning `void` and calling it unawaited - three statements that cannot all be true, since a `void` method cannot await and this plan forbids `GetAwaiter().GetResult()` outside a `Main` arm. The synchronous form is the correct one, not a concession: the sink's entire body is a `TryWrite` onto a `DropOldest` bounded channel, which never blocks and never awaits. The contract is written on the method - **a sink must not block, must not await, and must not throw** - and the only sink in the tree honours it by construction.
    - There is no bare `Subscribe`. Registration is inseparable from the backlog that must precede it; see Step 7 for why splitting them loses and reorders events.
  - `Findra.IndexLock` - `IDisposable Read(char volume)`, `IDisposable Write(char volume)`; one `ReaderWriterLockSlim` **per volume**.
  - `Findra.JournalTail` - `static IReadOnlyList<VolumeResume> ResumeFrom(IReadOnlyDictionary<char, ulong> journalIds, IReadOnlyDictionary<char, long> current, IReadOnlyList<VolumeCursor> from)`; `static int Apply(NameIndex ix, NtfsVolume.Change c)`; `static Task RunAsync(...)`; `const int MaxApplyBatch = 20_000`. `ResumeFrom` stays on plain dictionaries rather than `VolumeView` so it remains pure and testable with no `NameIndex` in sight; `Serve` projects the two dictionaries out of its `VolumeView`s in one line.
  - `delegate (bool Reachable, IReadOnlyList<JournalEvent> Events) GapReader(char volume, ulong journalId, long fromUsn)` - how a session catches a subscriber up from its stored position. The real one wraps `NtfsVolume.Read`; a test supplies its own, which is the only reason the gap replay is testable without a disk and without elevation.
  - `NameServer.Serve(Stream, IReadOnlyDictionary<char, VolumeView>, IndexLock?, JournalBroadcast?, GapReader?, CancellationToken)` plus the existing three-argument overload, which wraps each `NameIndex` in a `VolumeView(ix, JournalId: 0, NextUsn: 0, EnumerateMs: 0)` so Plan 1's tests keep compiling unchanged.
  - `NameServer.MaxOutbound` - **`public`**, because the back-pressure test reads it from the test assembly to publish past it.
  - `NameClient.SubscribeJournalAsync(IReadOnlyList<VolumeCursor> from, CancellationToken ct) : Task<SubscribeReply>`; `NameClient.JournalAsync(CancellationToken ct) : IAsyncEnumerable<JournalEvent>`; `NameClient.JournalDropped : long`.

```csharp
    [Fact]
    public void AnEventPublishedDuringASubscribeArrivesAfterTheBacklogAndIsNeverLost()
    {
        // The ordering test, and the reason SubscribeWithBacklog is one call rather than
        // "read the gap, then Subscribe". Two failures are possible with separate steps and
        // this catches both:
        //
        //   * register AFTER the gap read - an event published in between reaches no sink and
        //     is not in the gap either, so it is lost. `seen` comes back without "live.pdf".
        //   * register BEFORE the gap read and enqueue the gap afterwards - the live event is
        //     queued AHEAD of the older replayed records, so `seen` comes back live-first.
        //     That inversion is not cosmetic: a create-then-delete replayed behind a newer
        //     create of the same FRN makes the feeder delete a file that exists, and Enqueue's
        //     upsert on (vol, frn) does not save it - last write wins, and the last write is
        //     the older one.
        //
        // The backlog here sleeps deliberately, so a racing publisher has every chance to get
        // in first. It cannot, because Publish and SubscribeWithBacklog are mutually
        // exclusive: Publish parks for the length of one gap read and loses nothing, because
        // the tail's own NextUsn is untouched and it catches up on its next pass.
        var bus = new JournalBroadcast();
        var seen = new List<string>();
        var backlogStarted = new ManualResetEventSlim();

        Task racer = Task.Run(() =>
        {
            backlogStarted.Wait(TimeSpan.FromSeconds(5));
            bus.Publish(Event(900, "live.pdf", NtfsVolume.ReasonFileCreate, 78));
        });

        using (bus.SubscribeWithBacklog(
            backlog: () =>
            {
                backlogStarted.Set();
                Thread.Sleep(100);
                return [Event(700, "gap-1.pdf", NtfsVolume.ReasonFileCreate, 71),
                        Event(701, "gap-2.pdf", NtfsVolume.ReasonFileCreate, 72)];
            },
            sink: e => { lock (seen) seen.Add(e.Name); }))
        {
            Assert.True(racer.Wait(TimeSpan.FromSeconds(10)),
                        "Publish never returned - it must park for the backlog, not deadlock behind it");
        }

        lock (seen) Assert.Equal(["gap-1.pdf", "gap-2.pdf", "live.pdf"], seen);
    }
```

- [ ] **Step 4: `JournalBroadcast`**

A `Dictionary<long, Action<JournalEvent>>` keyed by a counter, guarded by one plain `lock`. `SubscribeWithBacklog` returns an `IDisposable` that removes its own key. `Publish` walks the sinks with a `try`/`catch` **per sink** - one dead session must never stop the others hearing the journal - logging the first such failure with `Log.Once`.

```csharp
/// <summary>
/// Registration is inseparable from the backlog that must precede it. `backlog` runs INSIDE
/// the lock and everything it returns is handed to `sink` before the sink can see a single
/// live event, so there is no window in which an event reaches neither the backlog nor the
/// sink, and no way for a live event to be delivered ahead of an older replayed one.
///
/// Splitting this into "read the gap, then Subscribe" is wrong in both orders. Register
/// second and an event published in between is lost - the smaller version of the very gap
/// this machinery exists to close. Register first and enqueue the gap afterwards and the
/// live event goes out ahead of older records: a create-then-delete replayed behind a newer
/// create of the same FRN makes the feeder delete a file that exists, and Enqueue's upsert
/// on (vol, frn) does not save it, because last write wins and the last write is the older.
///
/// A sink MUST NOT block, await or throw. The only sink in the tree is a TryWrite onto a
/// DropOldest bounded channel, which does none of the three - which is why this is an
/// Action and Publish is void.
/// </summary>
public IDisposable SubscribeWithBacklog(Func<IReadOnlyList<JournalEvent>> backlog,
                                        Action<JournalEvent> sink);
```

`Publish` takes the same lock. That means it parks for the length of one backlog read, which is a real cost and an acceptable one: the journal tail's `NextUsn` is untouched while it waits, so nothing is lost - it simply catches up on its next pass. Note it in the comment so nobody "optimises" the lock away.

- [ ] **Step 5: `IndexLock`**

```csharp
/// <summary>
/// One reader/writer lock PER VOLUME around the name indexes. Every Serve call reads them
/// concurrently and the journal tail now writes them - the exact situation the pipe's own
/// header warned about while the index was still immutable.
///
/// The strongest reason for this lock is not a crash, it is a WRONG ANSWER. LongIntMap.Rehash
/// (NameIndex.cs:549-556) replaces _keys and _vals as two separate field writes, so an
/// unlocked TryGet can pair a new key array with an old value array and hand back the wrong
/// record index - which is the wrong path, on a real result row, that a person then clicks.
/// Grow/Place/Trim have the same shape via Array.Resize. Shared reads, exclusive writes.
///
/// Per volume, not global: the indexes are already a per-volume dictionary, and a journal
/// batch on D: has no business stalling a query that only touches C:.
/// </summary>
public sealed class IndexLock : IDisposable
{
    private readonly ConcurrentDictionary<char, ReaderWriterLockSlim> _byVolume = new();
    public IDisposable Read(char volume)  => new Scope(For(volume), write: false);
    public IDisposable Write(char volume) => new Scope(For(volume), write: true);
    private ReaderWriterLockSlim For(char v)
        => _byVolume.GetOrAdd(char.ToUpperInvariant(v), _ => new ReaderWriterLockSlim(LockRecursionPolicy.NoRecursion));
    public void Dispose() { foreach (var l in _byVolume.Values) l.Dispose(); }
    // Scope enters in its constructor and exits in Dispose.
}
```

- [ ] **Step 6: `JournalTail`**

Four parts.

`ResumeFrom(journalIds, current, from)` is **pure** - it takes each volume's journal id, each volume's current `NextUsn`, and the caller's stored cursors, and answers where each volume resumes:

| Stored cursor | Answer |
|---|---|
| absent | `NeedsFullPass`, resume at the volume's current `NextUsn` |
| `JournalId` differs from the volume's | `NeedsFullPass`, resume at the volume's current `NextUsn` |
| `JournalId` matches | not a full pass; resume at the cursor's own `Usn`, and the session replays the gap |

Every `VolumeResume` carries the **current** journal id, never the caller's stale one - what the feeder stores has to be what the next launch will be compared against. `Note` says which of the three cases it was, in words a log reader can use.

`Apply(NameIndex ix, NtfsVolume.Change c)` mirrors the shape enumeration uses: a change carrying `ReasonFileDelete` removes by frn; anything else upserts `(Frn, ParentFrn, Attributes, Name)`. It returns how many records it changed, so the tail can log a rate.

`static JournalEvent ResetMarker(char volume, ulong journalId)` builds the one event that means *"your position is worthless"*: `Reason = 0`, `Name = ""`, `Path = ""` - **and the volume's real `JournalId`**, like every other event. Nothing keys off that id today, because `Consume` clears the position before it reads one; a zero that works only by accident is not worth keeping, and there is exactly one constructor so it cannot drift.

`RunAsync(volumes, gate, bus, ct)` is the loop, over the `VolumeView`s. Per volume: `vol.Read(vol.NextUsn, changes)`. A `false` return means the journal wrapped or was recreated, so log it and publish `ResetMarker(letter, vol.JournalId)`.

**Cap the apply.** `NtfsVolume.Read` (`NtfsVolume.cs:157`) drains the *whole* journal in one call - its inner loop runs until `next == StartUsn`. After a laptop resume or a long UI absence that single result can be hundreds of thousands of records, and holding the volume's write lock across all of them stalls every name query on that drive for the duration. Apply in slices of `MaxApplyBatch` (20,000), taking and releasing `gate.Write(letter)` per slice and publishing each slice before the next. A journal batch is only "short" if you make it short.

Within each slice, still under the write lock, `Apply` every change **and resolve each one's path in the same locked section**, building the `JournalEvent` list as you go: `Apply` first, then `ix.TryIndexOf(c.Frn, out int rec)` and `ix.PathOf(rec)`, so a create's path reflects the record that was just added. A delete resolves to `""`. Stamp every event with the volume's `JournalId`. Then, **outside** the lock, `bus.Publish` the slice.

Sleep one second and go again. Every exception is caught per volume and logged with `Log.Once`: a failing journal on one drive must never stop the other drives or take the helper down - names on whatever can be read is the floor (spec §12, known risk 4).

Wire it into `NameServer.RunAsync`: build the `IndexLock` and `JournalBroadcast`, build a `VolumeView` per volume as it enumerates - the `NameIndex`, the `NtfsVolume`'s `JournalId` and `NextUsn`, and the enumeration time it already measures and currently only logs - build the real `GapReader`, start `JournalTail.RunAsync` as a background task before `ListenAsync`, and pass the views, the lock, the bus and the reader through `ListenAsync` into each `Serve`.

**The real `GapReader`, spelled out, because it produces `JournalEvent`s and the mapping is not obvious.** `vol.Read` yields `NtfsVolume.Change`, which carries no path and no journal id, so the reader must do for replayed records exactly what the tail's slices do for live ones:

```csharp
// Catch-up read, on a PRIVATE NtfsVolume handle - never the tail's, whose NextUsn is live
// state the tail owns and which this must not move.
(bool Reachable, IReadOnlyList<JournalEvent> Events) ReadGap(char volume, ulong journalId, long fromUsn)
{
    var changes = new List<NtfsVolume.Change>();
    if (!catchUp.Read(fromUsn, changes)) return (false, []);      // wrapped, or recreated

    var events = new List<JournalEvent>(changes.Count);
    using (gate.Read(volume))                                     // shared: this only READS the index
        foreach (NtfsVolume.Change c in changes)
        {
            // Resolve against the index as it stands now. This does NOT apply the change -
            // the tail owns every write, and applying here would double-apply what the tail
            // already did. A record that has since been deleted resolves to "", which is
            // correct: the feeder keys deletes on (vol, frn) and never needs a path.
            string path = ix.TryIndexOf(c.Frn, out int rec) ? ix.PathOf(rec) ?? "" : "";
            events.Add(new JournalEvent(volume, journalId, c.Frn, c.ParentFrn, c.Attributes,
                                        c.Name, path, c.Reason, c.Usn));
        }
    return (true, events);
}
```

**Stamp `journalId` from the `VolumeView`, not from anywhere else.** If the replay path forgets it, `Consume` writes `(0, usn)` and the whole resume story dies on precisely the path the gap replay was added to fix. The test helper bakes a literal id into its synthetic events, so no test can catch this omission - it has to be right by reading.

- [ ] **Step 7: `NameServer.Serve`**

Take `IReadOnlyDictionary<char, VolumeView>` in place of the `NameIndex` dictionary, add the three new parameters, and keep the three-argument overload wrapping each index in a zeroed `VolumeView`. Then, the load-bearing part:

- **One `SemaphoreSlim(1, 1)` per session guards every write to the transport.** `AnswerQuery`, `AnswerStatus`, the subscribe reply and the outbound drain all take it. Without it the reply path and the push path interleave bytes into one stream and the framing never recovers.
- `case Envelope.KindSubscribe:` does all of this **inside one hold of the write semaphore**:
  1. compute `JournalTail.ResumeFrom(...)`, projecting the two dictionaries out of the `VolumeView`s;
  2. call `bus.SubscribeWithBacklog(...)`, passing a **backlog delegate** that calls the `GapReader` for each volume whose resume is *not* a full pass and returns the concatenated events in USN order. A `Reachable = false` answer flips that volume to `NeedsFullPass` with the note *"the journal no longer reaches that position"* and contributes nothing;
  3. write the `SubscribeReply`, carrying the `Replayed` counts the backlog produced.

  **The gap read happens inside the registration, not before it.** Two separate steps are wrong in both possible orders, and this is the second time this plan has had to be corrected on it - the reasoning is on `SubscribeWithBacklog` in Step 4 and in `AnEventPublishedDuringASubscribeArrivesAfterTheBacklogAndIsNeverLost`. In short: register second and an event published in between is lost; register first and enqueue the gap after, and live events go out ahead of older replayed ones, which makes the feeder delete files that exist.

  The client cannot see a journal frame before the ack, whatever the order inside the lock: the sink never touches the transport, and the drain task has to take the same semaphore this handler is holding.
- **The sink never writes to the transport.** It appends to a per-session bounded outbound queue - `Channel.CreateBounded<JournalEvent>(new BoundedChannelOptions(MaxOutbound) { FullMode = BoundedChannelFullMode.DropOldest })` - and returns. One drain task per session reads that channel, takes the write semaphore, and writes one frame at a time, which keeps ordering and keeps the tail free.
- **`public const int MaxOutbound = 32_768`, and it must be `>= JournalTail.MaxApplyBatch`.** This is not a tuning knob, it is a correctness bound. The tail publishes a slice of up to `MaxApplyBatch` (20,000) events, `Publish` fills the session channel synchronously because a `DropOldest` `TryWrite` never blocks, and the drain task writes one frame at a time over a named pipe. At 8,192 - the earlier draft's figure - a single ordinary catch-up slice drops roughly 11,800 events on a **perfectly healthy client**, which turns the drop path below from a pathological case into the normal one. Assert the relationship in a static constructor or a `--searchtest` check so a later edit to either constant cannot quietly break it.
- **A drop is a hole in the range the cursor is about to claim, so it must be impossible to lose.** Increment a per-session counter, surface it in `VolumeStatus.Dropped`, and **push a reset marker for that volume on every drop burst** - not once per session. "Once per session" means every drop after the first is silent, and later events then advance the cursor over holes nobody recorded. Coalesce within a burst if you like (one marker per volume per drain pass), but never suppress across the session.

  A drop the user is told about is recoverable. A silent one leaves the index claiming to be complete over a range it never saw, which is strictly worse than the gap the replay path was added to close, because that one at least announced itself as `NeedsFullPass`.
- The registration and the drain task are disposed in `Serve`'s `finally`, so a session that ends stops receiving.
- Every read of a `NameIndex` in `AnswerQuery` and `AnswerStatus` goes inside `gate.Read(letter)` when the gate is non-null, per volume, around that volume's whole scan. `AnswerStatus` fills `EnumerateMs` and `NextUsn` straight off the `VolumeView`.

- [ ] **Step 8: `NameClient`**

`SubscribeJournalAsync` writes one `KindSubscribe` frame and awaits its reply, matched positionally exactly as `StatusAsync` does - including the dead-waiter skip on dequeue, for the reason spelled out there.

`JournalAsync` is an `IAsyncEnumerable<JournalEvent>` over a `System.Threading.Channels.Channel<JournalEvent>`. Without that, a client-side drop is the one hole in the design that nothing records.

## Task 4: The first pass, and the queue the UI feeds

The UI decides what is indexed (spec §3). It has two sources: the journal events Task 3 pushes, and a first pass over everything already on the disk. The second one needs paths, and the only process that can produce a path cheaply is the helper - it holds the parent map in RAM.

**The first pass uses a new `enumerate` request, not a full snapshot, and the suffix filter travels on the wire from the UI.** A `Snapshot` that streamed every live record would send ten to twenty times the rows for the same answer, and the UI would then have to rebuild the parent map to turn `(frn, parent, name)` into a path - which is the entire name index, duplicated at normal integrity, in the one process the design keeps thin on purpose. `Enumerate` sends only the paths whose suffix the **caller** named, and the helper still decides nothing: the predicate is a list of strings that arrived in the request. All the actual policy - `HasContent`, exclusions, repo roots, size caps, the diff against what is already indexed - runs in the UI on the rows that come back.

- [ ] **Step 3: Implement enumerate**

Messages: the three records and two constants above, with a comment saying the suffix list is the caller's and the helper applies it mechanically - it holds no table of what a document is.

`NameServer.Serve` gains `case Envelope.KindEnumerate:`. It clamps `BatchSize` to `1..2000` and `Suffixes.Count` to at most 64 with each entry at most 16 characters - **never trust the frame**, and an unbounded suffix list is a per-record loop the caller controls inside the elevated process. Under `gate.Read()`, walk `0..ix.Capacity`, skip `!IsAlive` and `IsDirectory`, match `ix.Name(rec)` against the suffixes with `EndsWith(..., OrdinalIgnoreCase)`, resolve `PathOf`, and accumulate. Write a reply frame each time the batch fills, through the session write lock, and one final frame with `Done = true`. An unknown volume writes a single empty `Done` frame.

**Do not hold the read lock for the whole walk.** On a 1.5M-record volume that walk is seconds of `PathOf` calls, and `ReaderWriterLockSlim` gives a waiting writer priority over new readers - so one journal batch queued behind the walk blocks every subsequent `AnswerQuery`, and the card is unresponsive for as long as the enumeration lasts. That is the first pass, on every fresh install, which is exactly when someone is watching.

Take a **snapshot under a brief write-free hold instead**: under `gate.Read(letter)`, copy the matching `(frn, path)` pairs for one batch into a local list, release, write the frame, re-acquire for the next batch. Carry an epoch counter that `JournalTail` bumps on every applied slice; if it moved between two batches, restart the walk from record zero. A restarted walk costs a second; a duplicate or a missed file costs a wrong index, and the batches are already idempotent because `FillFrom` diffs against `KnownItems` before it enqueues.

State the cost in a comment: an enumerate that races a busy journal can restart, and on a volume under constant churn it could in principle restart repeatedly. Cap the restarts at three and then take the whole-walk read lock as a fallback, so the walk always terminates.

`NameClient.EnumerateAsync` writes the request with a fresh id (a plain `Interlocked.Increment` counter, **not** the generation), registers a `Channel<EnumerateReply>` under that id, and yields files until a `Done` frame arrives. The pump routes `KindEnumerateReply` by `Id`. This is why enumerate is id-matched rather than positional like status: it is many frames per request, and a positional queue cannot express that.

**`Eligible` is static, public and pure**, taking exclusions and repo roots as parameters rather than reading fields. That is what makes the table test above possible, and eligibility is the rule most likely to be argued about later.

```csharp
/// <summary>Worth opening: a kind with content, outside every exclusion, outside every
/// repository. A repository's fixtures, sample media and vendored documents are not the
/// user's library; their NAMES stay searchable, their contents are not read.</summary>
public static bool Eligible(string path, ResultKind kind,
                            IReadOnlyList<string> exclusions, IReadOnlyList<string> repoRoots)
    => FileKinds.HasContent(kind)
       && !FileKinds.Excluded(path, exclusions)
       && !UnderAnyRoot(path, repoRoots);

/// <summary>Under a root, not merely starting with its characters. Without the separator
/// test, a root of C:\Code\findra silently swallows C:\Code\findra-notes as well.</summary>
private static bool UnderAnyRoot(string path, IReadOnlyList<string> roots)
{
    foreach (string root in roots)
        if (path.Length > root.Length && path[root.Length] == '\\' &&
            path.StartsWith(root, StringComparison.OrdinalIgnoreCase)) return true;
    return false;
}
```

**`Consume` replaces `OnChange`**, taking a batch of `JournalEvent` rather than one host-specific change record. It classifies each event itself: `ReasonFileDelete` set means delete, `ReasonRenameOldName`/`ReasonRenameNewName` means rename, `ReasonDataChanged` means change. A delete is queued **only if `db.HasItem`**.

An event whose `Reason` is `0` and whose `Name` is empty is the tail's **reset marker**: clear that volume's stored USN position outright *and* `db.SetWalkOwed(vol)`. Keeping a position after the journal has thrown our place away is a claim to be caught up on a journal that no longer contains us - and clearing the position alone is not enough, because the very next batch writes a fresh one from later events and the index is back to claiming completeness within milliseconds. The debt has to outlive the clear, which is why it is a row in `meta` and not a field.

**The position carries the journal id, and it is written in the same transaction as the enqueues.** The id comes off the events themselves - `JournalEvent.JournalId`, which Task 3 added for exactly this. Per volume, in the batch's transaction:

```csharp
// A USN is a coordinate inside ONE journal. Store the id with it, or the next launch
// compares this number against a journal that has a different id, concludes the position is
// meaningless, and re-walks the entire disk - at every single start.
(ulong Journal, long Usn)? had = db.UsnPosition(vol);
if (had is null || had.Value.Journal != journalId || max > had.Value.Usn)
    db.SetUsnPosition(vol, journalId, max, tx);
```

Note the shape of that condition. "Only forwards" alone is wrong: when a journal is recreated its USNs restart near zero, so a strictly-increasing rule would pin the position inside a journal that no longer exists and the feeder would never record anything again. Forwards **within the same journal**, and unconditionally when the journal changed.

Recording the position outside the transaction means a crash between the two either loses work or repeats it, which is the same class of bug from the other direction.

**`FillFrom(char volume, ulong journalId, long throughUsn, IEnumerable<EnumeratedFile> files)`** takes the enumerate stream rather than a `NameIndex`, and is otherwise the source's diff: read `db.KnownItems()` once, skip anything already present at any finished state - **Indexed, Failed and Skipped all count as finished**, which is what stops a photo with no decoder being re-queued on every launch - skip anything `Eligible` rejects, enqueue the rest with reason `"new"`, all in one transaction. In that same transaction it stamps the position (`SetUsnPosition(volume, journalId, throughUsn, tx)`), stamps the suffix set (`SetSuffixVersion(ContentSuffixes())`), and **calls `ClearWalkOwed(volume, tx)`** - the one and only place the debt is discharged, and only once a pass has actually completed. A full pass that does not record where it finished is a full pass that happens again; a full pass that does not clear the debt is a full pass that happens forever.

It returns the number of **distinct FRNs** it queued, not the number of `Enqueue` calls it made. The enumerate walk restarts from record zero on an epoch change (Task 4 Step 3), so one `(frn, path)` can legitimately arrive twice in a single stream. `Enqueue`'s upsert on `(vol, frn)` keeps the queue correct either way, but a count of calls would not match `PendingCount()`, and `AFinishedIndexQueuesNothingOnTheSecondPass` asserts an exact `3`.

`throughUsn` is the volume's `NextUsn` **read before the enumeration started**, which the `SubscribeReply`'s `VolumeResume.Usn` carries. Taking it afterwards would silently drop every change made during the walk; taking it before means those changes are replayed, and `Enqueue`'s upsert on `(vol, frn)` makes the overlap free.

**`StoredCursors()`** reads every `usn:<letter>` row back as `VolumeCursor`s. It exists so the value the feeder wrote and the value handed to `SubscribeJournalAsync` are provably the same round trip rather than two pieces of code that happen to agree - which is what `AfterAFullPassAndARestartTheHelperIsAskedToResumeNotToReWalk` tests.

**`NeedsFreshWalk(char volume)`** is `db.SuffixesChanged(ContentSuffixes()) || db.WalkOwed(volume)`. The suffix half is Task 1 Step 5c's stamp doing its job: when a later version adds an extension to `FileKinds`, every existing install has only ever asked the helper for the *old* list, so those files were never enumerated and no journal event will ever mention the ones already on disk. Without this they stay invisible on every machine that had already finished.

The `WalkOwed` half is the drop path. **It is consulted every time round the UI's loop, not once at startup** - a hole opened at 11am is no less a hole for the app having launched at 9 - and because it is persisted, a restart in between still owes the walk.

**`NoteClientDrops(long journalDropped)`** is how the client-side hole gets recorded at all. The helper marks its own drops with a reset marker; a drop in `NameClient`'s receive channel has nothing upstream that knows it happened. The UI passes `NameClient.JournalDropped` in on every batch, and any increase calls `SetWalkOwed` for every volume currently subscribed - the channel is not per-volume, so the debt cannot be attributed more precisely, and over-walking is the safe direction.

**`SetRepoRoots`** still exists; the UI fills it by asking the helper to enumerate `.git` - one more `EnumerateAsync` call with the suffix list `[".git"]`, mapped to the parent directory of each hit. Sort the roots once, ordinal-ignore-case.

```csharp
/// <summary>
/// The words-in-documents answer. It reads the local index directly - no pipe: this database
/// is the UI's own file at normal integrity, and the helper has never seen it.
///
/// Content results are deliberately NOT merged with name results. They answer two different
/// questions, and blending them lets a file merely NAMED "lease" outrank the lease itself,
/// found by its words - which is precisely what the Content pill exists to ask for.
/// </summary>
public static SearchResults Search(ContentDb db, string raw, int max)
{
    var sw = Stopwatch.StartNew();
    var q = new SearchQuery(raw);
    string text = q.ContentText.Length > 0 ? q.ContentText : raw;

    var byPath = new Dictionary<string, SearchResult>(StringComparer.OrdinalIgnoreCase);
    foreach (ContentDb.SegmentHit h in db.Fts(text, max * 4))
    {
        if (!q.Allows(Path.GetFileName(h.Path), h.Path, h.Kind)) continue;
        if (byPath.ContainsKey(h.Path)) continue;      // bm25 order: the first is the best
        byPath[h.Path] = ToResult(h, 0.86f, text);
    }

    var rows = byPath.Values.OrderByDescending(r => r.Score).Take(max).ToList();
    string note = rows.Count == 0 && db.IndexedCount() == 0
        ? "Nothing indexed yet - Findra is still reading what is inside your files."
        : "";
    return new SearchResults(raw, rows, NamesMs: 0, ContentMs: sw.Elapsed.TotalMilliseconds,
                             ContentReady: true, Note: note);
}
```

```csharp
private static readonly CultureInfo Fixed = CultureInfo.InvariantCulture;

/// <summary>
/// One line about the content index, or nothing at all. Drawn by the card's footer and by
/// the capsule, which paints its progress line only when this is non-empty - a permanently
/// visible empty bar is what makes an idle widget feel busy.
/// </summary>
public static string Line(string state, long pending, long indexed, bool alive, bool rebuilt)
{
    string n(long v) => v.ToString("N0", Fixed);

    if (rebuilt && pending > 0)
        return $"rebuilding the index - {n(pending)} to go";
    if (rebuilt)
        return $"index rebuilt · {n(indexed)} files";
    if (pending == 0 && indexed == 0) return "";
    if (pending == 0) return $"index up to date · {n(indexed)} files";
    if (!alive) return $"{n(pending)} waiting - indexing is paused while Findra is closed";
    if (state == "paused") return $"{n(pending)} waiting - indexing paused";
    return $"indexing {n(pending)} · {n(indexed)} done";
}
```

The `!alive` sentence is the spec's, kept in the spec's words. It is what the card and capsule show at startup when a previous session left a queue: indexing runs only while Findra runs (§3), so a backlog is expected and must be explained rather than looking stuck.

The `rebuilt` branch is spec §2a's other half - an index that was unreadable is rebuilt **and the UI says so**. It is checked first, and it survives the queue draining, because "why did this take an hour" is a question someone asks after it finishes.

Every number goes through `Fixed`. The line is compared in tests and read by users on machines set to any locale; `{n:N0}` alone renders `9.000` in German.

**One honest imprecision, worth a comment in the code:** this says *"up to date"* on `pending == 0` alone. Spec §2a's stricter definition is a queue that is empty **at a journal position the volume still recognises**, and the position is only checked at subscribe time. The gap is a window where the journal wrapped since the last subscribe and the line is optimistic for one session. Note it rather than let it read as the spec's claim; closing it properly means asking the helper on every status refresh, which is a pipe round trip per second for a string.

- [ ] **Step 3: Write the report**

```csharp
public static double Percentile(IReadOnlyList<double> samples, double p)
{
    if (samples.Count == 0) return double.NaN;
    double[] s = [.. samples];
    Array.Sort(s);
    int rank = Math.Clamp((int)Math.Ceiling(p * s.Length), 1, s.Length);
```

Sorting inside is deliberate: a percentile helper that silently requires sorted input is a defect waiting for its second caller.

- [ ] **Step 4: `Machine.Read()`**

Five lookups, each independently wrapped so one failure costs one field and prints `unknown` rather than taking the mode down:

| Field | How | Why not the obvious thing |
|---|---|---|
| CPU | `HKLM\HARDWARE\DESCRIPTION\System\CentralProcessor\0` → `ProcessorNameString` | no WMI dependency, no admin rights |
| Architecture | `RuntimeInformation.ProcessArchitecture` | nothing here may assume x64; an arm64 run must be self-identifying |
| RAM | `GlobalMemoryStatusEx` → `ullTotalPhys` | `GC` memory info reports the process, not the box |
| Disk | two `DeviceIoControl` calls, both unelevated - see below | `DriveInfo` knows nothing about the medium |
| Windows | `RtlGetVersion` from `ntdll` for major/minor/build, plus `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\UBR` for the revision | `Environment.OSVersion` is shimmed by the manifest and lies about the build |
| Accelerator | the literal `"CPU only - this build runs no models"` | this plan runs no model, so naming a provider would claim code that does not exist - and the string is pasted onto a product page, so it must read as a fact about Findra, not as a note to ourselves |

**The disk lookup, spelled out, because the obvious version needs administrator and this mode does not have it.** It is two steps:

1. **Volume → physical drive.** Open `\\.\C:` and issue `IOCTL_VOLUME_GET_VOLUME_DISK_EXTENTS` (0x560000). The first `DISK_EXTENT.DiskNumber` in the result is `N` in `\\.\PhysicalDriveN`. There is no other supported way to find it, and guessing `PhysicalDrive0` is wrong on any machine that boots from the second disk.
2. **Physical drive → medium and bus.** Open `\\.\PhysicalDriveN` and issue `IOCTL_STORAGE_QUERY_PROPERTY` twice: `StorageDeviceSeekPenaltyProperty` (7) gives `IncursSeekPenalty` (false = SSD), and `StorageAdapterProperty` (1) gives `BusType` (`BusTypeNvme` = 17, `BusTypeSata` = 11, `BusTypeUsb` = 7). Render `"NVMe SSD"`, `"SATA SSD"`, `"SATA HDD"`, `"USB SSD"`, and so on.

**Open both handles with `dwDesiredAccess = 0` and `FILE_SHARE_READ | FILE_SHARE_WRITE`.** Zero access is the whole trick: it asks for a handle that can carry an IOCTL and nothing else, and it succeeds for an ordinary user. `GENERIC_READ` on either handle requires administrator, and because the fallback in this file is a silent per-field `unknown`, getting that wrong means the disk line reads `unknown` on **every** machine and nobody ever finds out. Use `File.OpenHandle`'s P/Invoke sibling `CreateFileW` directly - the .NET file APIs do not expose a zero-access open.

## Done when

- `findra --searchindex` prints the schema version, each volume's consumed USN **and the journal id it belongs to**, counts by kind, the indexer's state and a failure sample with an honest remainder - on a fresh machine with no index, and without elevation.
- `findra --searchindex "C:\some\folder" q:word` queues those files, drains them in-process, and finds the word.
- With the helper running, the UI subscribes to the journal, a file saved anywhere on a fixed drive appears in the queue within a couple of seconds, and its words are searchable once the child has taken it.
- **A file saved while Findra was closed is queued when Findra starts.** The subscribe replays the gap from the stored cursor; only a journal that no longer reaches that position forces a full pass. `ASubscriberBehindTheTailIsSentTheGapItMissed` and `AGapTheJournalNoLongerReachesAsksForAFullPassInstead` are the two tests that say so.
- **No event is ever silently skipped.** A dropped event or a reset marker leaves a fresh walk owed in `meta`, the debt survives a restart and cannot be erased by later events, and only a completed `FillFrom` discharges it. The index never claims to be complete over a range it did not see. `AResetMarkerLeavesAFreshWalkOwedThatLaterEventsCannotErase`, `TheWalkOwedByADropSurvivesARestart`, `ADropInTheClientsOwnChannelAlsoOwesAWalk` and `AFullPassDischargesTheDebtAndNothingElseDoes` are the four tests that say so - and `MaxOutbound >= MaxApplyBatch` is what keeps the drop path exceptional rather than routine.
- **A replayed gap reaches the feeder ahead of the live events published beside it**, so a create-then-delete from the past can never be applied after a newer create of the same file. `AnEventPublishedDuringASubscribeArrivesAfterTheBacklogAndIsNeverLost` is the test that says so.
- Pressing **Content** in the card answers from the words inside files, with an excerpt on each row, one row per file, and the query grammar still applied.
- **Quitting Findra stops indexing, and restarting it resumes the queue** - the pending count picks up where it left off, and nothing already indexed is redone. `AFinishedIndexQueuesNothingOnTheSecondPass`, `ANonEmptyQueueSurvivesTheProcessAndIsResumedNotCleared` and `AfterAFullPassAndARestartTheHelperIsAskedToResumeNotToReWalk` are the three tests that say so.
- A photo or an audio file is **Skipped with a reason**, never Failed, and `RequeueKinds` picks up exactly those - `state IN (1, 3)` - and nothing else.
- An index that cannot be opened is moved aside, rebuilt, and **said out loud** in the card and the capsule.
- `findra --searchbench bench.md` writes a Markdown fragment that pastes into the README unedited, naming the CPU, architecture, RAM, disk class, Windows build and accelerator, carrying per-volume enumeration time, name counts and resident bytes, the pipe/scan split, per-store sizes, and a unit and a sample size on every number - identical on a machine set to any locale.
- `dotnet test` green, `dotnet build -warnaserror` clean, `grep -ric prism src/ tests/` = 0, and a human-read comment pass done and reported.

## Execution notes

Task boundaries are drawn where a reviewer could reject one and approve its neighbour. The dependency shape:

```
1 (store) ──┬── 2 (indexer child)  ────────────────┐
            │                                       ├── 7 (--searchindex) ─┐
            ├── 3 (journal push) ── 4 (feeder) ─────┤                      ├── 9 (close-out)
            │                          │            │                      │
            └── 6 (content branch) ────┘            └── 8 (--searchbench) ─┘
                     5 (config) ───────┘
```

- **Task 1 is the gate.** Nothing else compiles without `ContentDb`. Do it alone, first.
- **Tasks 2, 3 and 5 are independent of each other** once Task 1 lands. File ownership: Task 2 owns `Content/{DocText,Indexer,IndexerHost}.cs`, Task 3 owns `Pipe/*` and `Names/JournalTail.cs`, Task 5 owns `App/Config.cs`. No overlap, so they can run concurrently. Task 5 is small and pure; if you are batching, fold it in beside Task 2.
  - Caveat: Task 2 and Task 8 both add a `Program.cs` switch arm, and Task 2 is the earlier of the two. See the note on 7 and 8 below - the same resolution applies.
- **Task 4 must be serial after both 3 and 5.** It shares `Pipe/Messages.cs`, `Pipe/NameServer.cs` and `Pipe/NameClient.cs` with Task 3 - three files, all edited by both - and it consumes `Config.SearchExclusions`. Its test file will not compile without either. If you reach Task 4's tests and the config fields are missing, do Task 5 first rather than stubbing them.
- **Task 6 needs 1 and 5**, not 3 or 4 - the content branch reads a database that a `--searchindex` drain can fill by hand. It owns `Card/CardWindow.cs` and `Content/{ContentBranch,IndexStatus}.cs`; Task 4 owns `App/App.axaml.cs`. No clash, so 6 can run in parallel with 3 and 4.
  - One coupling that is not a file conflict: Task 4 Step 9 creates the process's single `ContentDb` and Task 6 Step 5 consumes it. Whichever lands second wires the handoff.
- **Tasks 7 and 8 are NOT independent, despite being logically separate.** Both add a switch arm to `src/Findra/Program.cs` and a line to `Unknown()` - the same two places in the same file. Plan them in parallel if you like, but do not merge them blindly: expect a conflict in the switch, and resolve it by keeping both arms and both help lines. Everything else about them is disjoint (`Diagnostics/SearchIndex.cs` versus `Diagnostics/{SearchBench,Machine}.cs`), and both formatters are pure with tests that need no disk. Both need 1, 2 and 6.
- **Task 9 is last, and is not optional.** The lineage comment pass in particular cannot be delegated to a grep, and two earlier plans have had ported material survive one.

Two things in this plan cannot be verified by an unelevated agent: Task 3's Step 10 and the name and volume halves of Task 8. Both have a defined non-elevated outcome - stop at the build, and print "the name helper is not running" with no tables respectively. Say which one you hit; do not fake either.
